# MHL LIMS pilot

A working, hands-on version of the new LIMS for trying the workflows with test data. It covers lookup, new requests from NAS (with IHC stains chosen from the catalog), Zaphod-style necropsy and trim protocols, necropsy and pathology with printable reports for each animal, an organ and diagnosis library with INHAND and SEND terminology, bloodwork (hematology, chemistry and cytology, with imports from the Genesis, VS2 and Piccolo), whole-slide imaging (registering images from the Aperio AT2, GT 450 and FL and the Akoya PhenoImager HT), an antibody dilution calculator, study summaries, the IHC assay catalog and IHC requests (from the old phlrequest site), charges, billing QC and billing batches.

**It is a pilot, not the production system.** Apart from the IHC assay catalog, which is MHL's real assay list, everything in it is fictional test data. It runs for one person on one computer and has not been through security review. Do not enter real study, patient or billing information.

## Start it

**On Windows:** double-click **`Start MHL LIMS pilot.cmd`**. A black window opens and your browser opens the pilot at `http://localhost:3080`. Keep the black window open while you use it; close it to stop the pilot.

**Any computer with Node.js:** open a terminal in this folder and run `node server.mjs --open`.

It needs **Node.js 18 or later** and nothing else: no installation step and no internet connection. It only listens on your own computer (127.0.0.1), so no one else on the network can reach it.

**No Node.js?** Open `dist/MHL-LIMS-pilot-standalone.html` in Edge or Chrome. It is the same pilot in a single file, with the data saved in that browser.

The first time it opens it asks for your initials, which it stamps on everything you record.

## Things to try (about an hour)

1. **Look up.** The open requests list shows, for each request, what has been charged so far against the estimate sent to NAS, with the NAS authorization below; Okafor's ZAP2215 request is over its estimate. Search `Okafor`, a PHL number such as `26000305A`, `ZAP2215`, or a NAS number such as `26-0412`; request results show the same billing figures. Open the request: every request has the same tabs, in this order: **Overview** (where every PHL number is, and the funding), **Labels**, **Estimate**, **Necropsy**, **Bloodwork**, **Pathology**, **Slide images**, **Charges** and **History**. Tabs for work the request does not include are grayed and say so. The **Necropsy** tab lists each PHL number's necropsy (status, date, prosector, fate, body weight, organs collected, gross findings) with links to the reports and, for a study, the study necropsy report.
2. **Start a request from NAS.** Every new request starts under **New request**: from an approved NAS request, or from an IHC request sent through the web form (step 11). Choose Abernathy's NAS request. Check the details, create a new study (it names a necropsy protocol and a trim protocol), then on **Stains and IHC** search the catalog for an antibody by target or clone (try `CD8`, `RAM34` or `F4/80`) and add it; each result shows the clone, host and clonality read from the catalog, and protocols that fit the species and fixative come first. Adjust the estimate, which now includes the stains, then create it. Note the PHL numbers, print the labels, and open the **IHC worksheet** (under Molecular) it created.
   - **Several requests from one NAS request.** A NAS request stays in the list after its first request, for example a pilot and then the main study. Choose **Another request from NAS# …** on the page after creating one, or open **NAS requests that already fund a request** in the list. The estimate step shows what the other requests are estimated at or have been charged and checks the new one against what is left; their charges count against the shared authorization on every request page. **Close NAS request** when no more requests will come from it (**Show closed NAS requests** reopens one). If the NAS request came from an estimate in phases, the estimate step can start from one phase at a time, and each request remembers its phase.
   - **Animal list from the investigator.** On **Request details**, **Read the investigator's spreadsheet** and choose `samples/animal-lists/Abernathy-animal-list.xlsx`: the investigator's own workbook, with a title row, their own headings (Mouse #, Gender, DOB, Cage #, Comments) and a column MHL does not read. The LIMS finds the list on the right tab, says which heading fed which column, and shows every animal. **Use these 16 animals**: the request gets one PHL number per animal, in the list's order, each with its ID, sex, strain, date of birth, cage and notes, and the new study gets groups G1 to G4 with their treatments. The labels, tracking sheet, necropsy screen (with a sex-specific organ list) and reports show the details. Try `animal-list-with-problems.csv` too: each mistake is shown by line, and the list cannot be used until it is put right. **Download the template (.xlsx)** gives investigators a workbook to fill in, with the request details on top, drop-downs for sex and priority, and an instructions sheet. Human samples and organoid lines keep no dates of birth.
   - Sato's request shows what happens when the estimate is more than NAS authorized.
   - On **Request details** you can record the **tissue disposition** (what happens to leftover tissue, for example `RTRN`, returned to the investigator), as PHL.exe did.
   - On **Create and label**, the request number is the next automatic number unless you choose **Enter the number by hand**, for example to carry over a PHL.exe request ID such as `270333` or `270333A`. The number is checked as you type: it must be new, and its last five characters must not match another request of the same lab, because the Rpt080 billing extract knows a request by its lab letter and those five characters (try `260097`, which clashes with HP260097). A number typed by hand does not use up an automatic number.
   - After creating it, **Print tracking sheet** opens the MHL Request Tracking Form, laid out like the one PHL.exe printed: the request on top (with a barcode of the request number), then each PHL number with inits, proc and units rows under every work area, six PHL numbers to a page and a new page for each priority. Shaded columns are work areas the request does not include. Print it landscape on letter paper and send it with the samples. The sheet is also on every request's **Labels** tab; tick **Fill in work already recorded in the LIMS** to reprint a sheet part way through with the initials and dates so far.
3. **Necropsy.** Under **Necropsy**, open Brennan's study ZAP2231 (three animals are STAT). For each animal:
   - Enter the body and organ weights, add a gross finding, tick **Matches cage card**, and approve.
   - The approval creates the necropsy and lung perfusion charges and moves the animal on to trimming.
   - Use **Next animal** to keep going. Try **Unapprove to correct** on one.
4. **Pathology.** Under **Pathology**, the worklist shows every open case, from necropsy or from submitted slides, with who it is assigned to. Brennan's animals wait until their necropsy is approved.
   - In ZAP2215, **Start** animal 7. The tissues come from the necropsy, with their block numbers and gross findings. Click **Lesions** on the lungs and add a diagnosis such as `Adenoma, bronchiolo-alveolar`. Neoplasms ask for benign or malignant; other diagnoses ask for a severity grade (1 minimal to 5 severe). Tick the gross nodule it explains.
   - Mark the liver and spleen **NSL** (or add diagnoses), then use **Unread tissues: Not examined** for the rest. Every gross finding must be explained by a diagnosis or marked **No microscopic correlate**. Watch the **Before sign-out** checklist empty.
   - **Sign out** locks the report, charges PA001002 per glass slide read (tissues on the same block count once) and moves the animal to Complete.
   - **Amend report** on a signed case: it needs a reason, keeps the earlier version, and later bills only slides beyond what was already billed.
   - Haddad's request (PA260008) is slides submitted without necropsy: the pathologist adds the tissues. Animal 3 has a recut request, which shows on the worklist.
5. **Reports.** Every animal has a printable **Necropsy report** and **Pathology report** (from the case, the study's animal list or the request's Pathology tab). They show the microscopic diagnoses, the gross-to-microscopic correlation, cause of death, the pathologist's comment and the electronic sign-out, with amendment history. **Print all signed reports** prints a request's or study's reports one per page.
6. **Study summary and study reports.** Open **ZAP2215**: groups, animals, organ weights (absolute and relative) with group means and 95% confidence intervals, gross findings incidence, and the animal-level CSV for R or Excel. The **Pathology** section has the incidence of each microscopic finding by group with mean severity, neoplasm counts, the individual animal table and a diagnoses CSV.
   - **Study necropsy report** (on the study page, and on the Necropsy tab of its requests) prints, for every animal in the study by group: the groups, each animal's disposition (necropsy date, fate, body weight, prosector), the gross lesion incidence table and each animal's gross findings, organ weight tables with a dot plot per organ (absolute and relative), and the bloodwork: group means and a scatterplot of every animal for each analyte, with the reference range shaded and values outside it ringed.
   - **Study pathology report** prints the incidence of microscopic findings by group (with mean severity), the neoplasm tables (summary and by organ, benign, malignant or metastatic), and each animal's findings by group: a tabulated grid per group, then each animal's diagnoses, cause of death and sign-out. Unsigned reports are counted and left out.
   - Incidences are compared with the first group by Fisher's exact test (two-sided, not adjusted for multiple comparisons): * p < 0.05, ** p < 0.01. Each report has a **Summary** box for the narrative, printed at the top.
7. **Charges.** On a request's **Charges** tab, do each of these:
   - Add a charge. Labor and reagent codes ask for a description, and codes without a price are refused.
   - Approve or void a pending line.
   - Adjust a released line.
   - Record the billing QC review.
8. **Billing.** Under **Billing**, approve the pending charges, preview a batch for the HP lab, then release it. The billing file downloads in PHL's Rpt080 format, and those charges are now locked.
9. **History.** Every request has a tracking history and an audit trail of who did what, and when.
10. **IHC assay catalog.** Under **Molecular** (formerly IHC), open **Assay catalog**. It holds the IHC database export: 756 protocols, plus 22 double stains built from the "DOUBLE STAIN" rows.
   - Filter by species, fixative or kind (IHC, multiplex, fluorescent), or search `CD8`, a clone or a catalog number. The main **Look up** search finds antibodies too.
   - Tick **Needs checking** to see what the import repaired, such as dilutions Excel had turned into times. Open one, confirm it, and **Mark as checked**, or **Edit** it. Every change is in the assay's history.
11. **IHC requests.** Requests investigators send from the IHC request site (phlrequest) are reviewed under **New request**, below the NAS requests; once accepted, the work is assigned and done under **Molecular**.
   - Under New request, review **MH26-0154**: it copies the shape of a real request (mouse liver, CD8 ab101500). The LIMS warns that the tissue has been in formalin for 339 days and that this CD8 protocol is listed for human tissue.
   - Review **MH26-0153**: its four lung blocks are already PHL numbers from ZAP2215, and the page links them. **Accept** it, choosing Okafor's NAS request (which already funds ZAP2215's request: a NAS request can fund several) or "Link a NAS request later". It becomes a request with PHL numbers and an estimate. **MH26-0152** includes an antibody that is not in the catalog.
   - Under **Molecular**, **IHC requests** lists the accepted ones: MH26-0151 is assigned to LW and in progress; the one you accepted is unassigned. Tick it and **Assign selected to** someone's initials, or open it and use **Start** and **Done**. Its page has the bench worksheet (formerly a tab on the request) and **Antibody volumes**.
12. **Antibody dilution calculator.** Under **Molecular**, open **Antibody dilution calculator**.
    - **Dilution ratio (1:X)**: a dilution and a final volume give the antibody and diluent volumes (1:X is one part in X in total, as on datasheets). Add the stock concentration to see the working concentration.
    - **Concentration (C1V1 = C2V2)**: choose which value to calculate (stock volume, stock concentration, working concentration or final volume) and enter the other three, with units.
    - **For a run of slides**: add antibodies from the catalog. Their dilutions are read from the catalog (a 6-plex panel gives one row per antibody), and the volume per slide defaults to 150 µL for the Leica BOND and 100 µL for manual staining; change it to match your instrument. Spare and dead volume are added. Under the smallest volume you pipette, it suggests an intermediate dilution. **Print prep sheet** gives a bench copy.
    - From an assay page, **Dilution calculator** opens it for that assay; from an accepted IHC request's worksheet, **Antibody volumes** opens it with every stain and one slide per block plus a control.

13. **Protocols.** Under **Necropsy**, open **Necropsy and trim protocols**. As in Zaphod, a necropsy protocol lists the organs in order (fixative, freezing, weigh, measure, instructions) and a trim protocol puts each organ in a block, by sex.
    - Choose **Import from Zaphod** and the file `samples/zaphod/zaphod-export-sample.json` (fictional protocols in the exact format of the real export). Read what it would change, then import. ZAP2215 now uses the sample lung tumor protocols.
    - Open a protocol, change a step and save: an approved protocol needs approving again. Try **Copy** and **Make obsolete**.
    - Point Brennan's study ZAP2231 at "Sample - mouse full necropsy" and its trim protocol, then start a necropsy on one of its male mice: the organ list has testes but no ovaries, with blocks and the snap-freeze instruction from the protocols.
    - To load MHL's real protocols, run `../tools/zaphod-export/export_zaphod_reference.sql` against Zaphod (read-only; C&SS may need to run it) and import the file it saves. It also brings Zaphod's dictionaries and reference ranges.
14. **Terminology.** Under **Pathology**, open **Organ and diagnosis library**. Every term has its INHAND organ system and the SEND value it would be submitted as, marked "to check" until the official SEND terminology is loaded.
    - Download *SEND Terminology.txt* from NCI EVS (free) and choose it on this page: the pilot checks every term, adds the NCI codes, and lists what needs a SEND value chosen.
    - Add a term or correct one; with SEND loaded, the SEND box searches the official codelist.
    - In a pathology case, the diagnosis box shows each term's system, and its SEND value once chosen. On a study page, **Download microscopic findings, SEND style** gives the signed findings with SEND specimen, finding, severity and laterality.
15. **Bloodwork.** Under **Bloodwork**:
    - **To review** has two ZAP2215 results waiting. Open one, check it, and **Release** it: that creates the CBC or VetScan panel charge. **Reopen** a released result to see the charge voided.
    - **Import results**: choose the files in `samples/instruments` (three VS2 PuTTY logs, a Piccolo session with two printouts, and a Hemavet DMS export as .xls and .csv) for Brennan's mice. One Piccolo printout has a mistyped sample ID, `2600331A`: it waits under **Sample IDs that are not PHL numbers** until you assign it to `26000331A`. Importing the same file again is skipped.
    - **Listen to an analyzer** (Edge or Chrome): replaces PuTTY by reading the VS2 or Piccolo serial port directly. With the server version, **Read the instrument folders** imports every file in the folders set in Settings, like Zaphod's Read Files buttons.
    - **Cytology**: open the bone marrow smear for ZAP2215 animal 2 (differential, M:E ratio, signed), or start a blood smear for any PHL number.
    - **Reference ranges**: set the lab's ranges by species; results are flagged against them, or against the range on the printout when none is set. Importing the Zaphod export fills them.
    - Each animal has a printable **Bloodwork report**, each request a **Bloodwork** tab, and ZAP2215's study page a bloodwork summary by group with a CSV.

16. **Whole-slide imaging.** Under **WSI**:
    - **Scan queue** lists the PHL numbers in the Scan area by request, with the scanner and magnification to use: Lindqvist's Opal panel goes to the PhenoImager HT, Rivera's 40x boxes to the GT 450, ZAP2215's H&E to the AT2. **Print scan list** gives a loading sheet; **Scanning done** moves the selected PHL numbers on (only once their images are reviewed).
    - **To review**: open the PhenoImager HT image for 26000312A (seven Opal channels), then **Pass** it, which creates the HP001009 scan charge, or tick reasons and **Rescan**. `Slide_0017.svs` had an unreadable barcode: assign it to a slide such as `26000325A-S04`.
    - **Register images**: choose the files in `samples/scanners` (two GT 450 slides for Rivera's box 2, an AT2 H&E for 26000307A, an Aperio FL image with its three channel files, a PhenoImager HT .qptiff for 26000313A, and one slide with no barcode). Or choose a folder: in Edge or Chrome, pick a scanner's output folder and read it again after each run; images already registered are skipped. Only the start of each file is read, so multi-gigabyte images are quick, and nothing is copied.
    - **Scanners**: each scanner's status, the instrument IDs found in its files (so images land on the right scanner) and, for the server version, its output folder, which **Read new images** reads like the bloodwork folders.
    - Each request has a **Slide images** tab; each image page shows what the scanner wrote, the channels, the file path, and a place for a HALO Link or eSlide Manager address.
    - The sample files are tiny stand-ins with the scanners' header structure, not real images. Try the import on real files from each scanner (open question 36).
17. **Estimates.** Under **Estimates**, cost estimates for possible new projects, made before the investigator submits a NAS request:
    - The list shows the test estimates in every state: Halvorsen's draft, Castellanos's sent revision 2 (revision 1 is kept), Moreau's accepted one, Brennan's declined one and Iverson's expired one. Search by estimate number, investigator, institute or project; **Look up** finds estimates too.
    - Open **Halvorsen's draft**. It has two phases (a pilot of 8 mice and a main study of 32), CD8 and Ki-67 IHC on the tumors, and an optional clinical chemistry line shown but not counted. Change units or add a note and the totals follow as you type; the draft saves itself.
    - Each phase has four ways to add lines: **Fill in from a kind of work** (the usual lines for, say, a full necropsy, for any number of animals and blocks per animal), **Add a charge code** (search the price list), **Add IHC and stains** (antibodies from the IHC catalog, priced by the same rules as New request) and **Add a line not on the price list** (such as a Xenium run, with a price or "to be confirmed"). Codes the list has no price for, and labor or reagent codes that need a description, are flagged until they are sorted out.
    - **Print preview** gives the estimate to send: the lines by phase, optional lines, assumptions and terms. Its prices are fixed when it is sent, and it is valid for 90 days (you can change that per estimate).
    - **Email…** prepares the email to the investigator: To, Cc (for example the lab's shared mailbox), subject and a suggested message and sign-off, with a preview of what the investigator will see. **Open in Outlook** downloads an email file; open it from the browser's downloads and Outlook shows a new message, addressed and ready, with the estimate laid out in it and the lines attached as a spreadsheet. Check it and click Send in Outlook (the pilot never sends email itself, so a copy stays in your Sent Items). **Copy the email** is for Outlook on the web, or if the file opens as a received message: paste it into a new message. **Other email program** opens your default email program with plain text. Emailing a draft marks it as sent; a draft can also go to a colleague for review and stay a draft. Each email is listed on the estimate. To send it yourself instead, print it (or save it as a PDF) and use **Mark as sent**.
    - On a sent estimate record the answer: **The investigator accepted it**, **Declined** (with a reason), or **Revise**, which starts revision 2 with today's prices. An expired estimate must be revised before it can be accepted. **Copy as a new estimate** starts a new one from any estimate.
    - Link an accepted estimate to the investigator's NAS request (or, in the pilot, make the NAS request from it). Its price list lines become the NAS request's scope, so **New request** starts from them; try Moreau's NAS request 26-0477 under New request. Lines not on the price list are listed there for you to add with a code.

18. **Xenium.** Under **Molecular**, open **Xenium**.
    - **Waiting for a run** lists PHL numbers in the Xenium work area: ORG-3 of Petrakis's organoid lines waits for a recut. ORG-1 and ORG-2 are on run **XR26-0001** (Xenium Prime 5K human panel, two slides, assigned to JM), now at probe hybridization.
    - Open XR26-0001 and **Mark done** each step: on the Xenium Analyzer (the slide serial numbers are needed first), instrument run complete, post-run H&E, data delivered. Delivery moves the PHL numbers on to their next work area (scanning, here). Record the run's quality numbers and output folder; **Undo the last step** and **Failed or cancelled…** (which puts the sections back in the queue) are there too.
    - Tick ORG-3 and **Plan a run**: choose the assay and panel (the LIMS warns when a panel does not fit the material), who it is assigned to, and which slide each section goes on (two slides per run).
    - The CY2027 price list has no Xenium charge code, so runs make no charges (open question 47).

## Your data

- **Where it's saved.** Data is kept in `data/mhl-lims-pilot.json` in this folder. A dated copy goes to `data/backups/` the first time it changes each day.
- **Backup and reset.** **Settings** (click your initials) can download a backup or reset to fresh test data dated today.
- **Pricing.** Prices come from the CY2027 billing worksheet. In the pilot they apply from 1 January 2026, so today's work can be charged. The real contract-year start is still an open question, and you can change this date in **Settings**.
- **Used the pilot before?** Your data keeps everything you entered and is upgraded automatically: each study keeps its protocol (now as a necropsy protocol and a trim protocol with the same name), and the library, protocols, bloodwork, slide imaging (with the four scanners), an empty list of estimates and Xenium runs are added. NAS requests whose requests are all complete are closed; the others stay open for more requests. The sample bloodwork, slide images, estimates and Xenium run only appear after **Settings > Reset pilot data**.
- **Sample instrument files** match the test data's PHL numbers for 2026. After a reset in a later year the PHL numbers change, so imported samples arrive as unmatched; assign them by hand.

## How it relates to the real system

The pilot runs the same pricing and billing rules as the production C# code; `tools/rules-reference/rules.mjs` mirrors `src/MhlLims.Domain` rule for rule. Its data model follows the SQL schema in `/db`. It differs on purpose in these ways:

| Pilot | Production plan |
|---|---|
| One person, initials typed in | NIH single sign-on with roles |
| A JSON file on this computer | SQL Server with temporal history |
| NAS requests typed in by hand | Read from NAS automatically |
| Labels printed from the browser (Code 128) | ZPL to thermal printers; DataMatrix on slides |
| Animal lists read from a spreadsheet the investigator emails | Investigators upload the list with their request in the Phase 4 portal; the same checks apply |
| IHC work and Xenium runs assigned by typing initials | Assignment from the staff list with roles, from sign-on |
| Xenium runs recorded by hand step by step | Run status and quality numbers read from the Xenium Analyzer's output, if 10x's files allow it (open question 54) |
| Estimate emails prepared by the pilot and sent from the user's own Outlook; the answer recorded by hand; the NAS request linked by hand | Estimates sent by the LIMS server from a shared MHL mailbox, with any approval the lab wants before sending (open questions 45 and 51); NAS requests that quote an estimate number linked automatically (open question 48) |
| The tracking sheet printed from the browser on letter paper, filled in by hand | The same sheet while the lab wants paper; later, scanning the sheet's barcodes at each bench replaces the handwriting |
| Placeholder dictionaries and three necropsy protocols | Zaphod's dictionaries and protocols, migrated |
| Necropsy and pathology screens exist only here so far | Built in Phase 3 of the roadmap, informed by what staff think of this pilot. The rules and tables are already in `MhlLims.Domain/Pathology` and `db/070_necropsy_and_pathology.sql` |
| A starter diagnosis list in INHAND style (`core/pathology.mjs`) | Zaphod's diagnosis dictionary and per-study diagnosis lists, migrated |
| Sign-out with typed initials | Electronic signature tied to sign-on; 21 CFR Part 11 controls if GLP work is in scope |
| IHC catalog loaded from a CSV export, with repairs | Migrated from the phlrequest database itself, with its own IDs and history |
| IHC requests from investigators arrive only in the seed data (the investigator form was taken out of the pilot); stains are chosen in New request | An investigator portal with NIH sign-in replaces phlrequest in Phase 4; investigators see only their own requests |
| Slide images registered from file headers chosen by hand, a browser-picked folder, or the server reading folders | A service on the scanner shares registers images as they are written, with HALO Link (or eSlide Manager) links and image-analysis requests |
| IHC pricing rules in `core/ihc.mjs`, with assumptions noted | Ported to `MhlLims.Domain/Ihc` with the assumptions still marked; confirm with billing (open question 18) before go-live |
| Three placeholder protocols, or Zaphod's imported from a JSON export | Zaphod's protocols migrated, with approval and change history in the database |
| SEND values guessed until the official SEND terminology file is loaded by hand | The SEND codelists loaded and refreshed with each CDISC release; INHAND criteria from goRENI |
| Instrument files imported by hand, from a folder, or by listening to the serial port in Edge or Chrome | A small local service on the instrument PCs sends results to the LIMS; no PuTTY |
| Bloodwork released by whoever is signed in | Release limited to the roles the lab chooses (open question 32) |

## For developers

- `core/`: application core (state and rules, no I/O), seed data, statistics, definitions. `core/protocols.mjs` holds the Zaphod protocol model, combining protocols per animal, and the readers for the Zaphod export and pasted tables. `core/terminology.mjs` holds the INHAND systems, the starter library with its SEND mapping, and the NCI EVS file reader. `core/bloodwork.mjs` holds the analytes, the VS2/Piccolo and Hemavet readers (Zaphod's layouts), flags and cytology. `core/sheets.mjs` reads .xls (BIFF8), .xlsx, CSV and HTML tables with no libraries. `core/ihc.mjs` holds the IHC rules: reading the export, classifying assays, matching them to samples, and pricing an IHC request. `core/pathology.mjs` holds the pathology dictionaries, diagnosis wording, sign-out checks and charges, slide counting and the study summaries. `core/necrules.mjs` holds the necropsy approval checks and charges.
- `core/wsi.mjs` reads TIFF and BigTIFF directories through a `readAt(offset, length)` function (so the browser and the server read only the header of multi-gigabyte files), parses Aperio .svs, Aperio FL .afi and Akoya .qptiff descriptions, finds slide IDs, and holds the scan charge rule. `core/dilution.mjs` holds the dilution arithmetic and reads catalog dilutions. `core/estimates.mjs` prices estimates; the browser and the core share it, so the totals shown while editing are the ones saved. `core/animallist.mjs` reads investigators' animal lists (finding the header row and the right sheet, checking every line) and lays out the template, which `core/xlsxwrite.mjs` writes as .xlsx with no libraries; `core/sheets.mjs` reads every sheet of a workbook. The sample lists are made by `../tools/animal-list-samples/make_animal_lists.py` (needs openpyxl). `core/estimatemail.mjs` builds the estimate email (HTML that Outlook can draw, plain text, the .eml file marked unsent, and the mailto: link) with no libraries. The sample scanner files are written by `../tools/wsi-samples/make_wsi_samples.mjs`.
- `web/`: browser UI (vanilla ES modules, no build step).
- `server.mjs`: HTTP server and file persistence.
- `build-standalone.mjs`: bundles everything into `dist/`.
- Tests: `npm test`, or `node --test test/core.test.mjs test/ihc.test.mjs test/pathology.test.mjs test/server.test.mjs test/v4.test.mjs test/v5.test.mjs test/v6.test.mjs test/estimates.test.mjs test/estimate-email.test.mjs test/v7.test.mjs test/animallist.test.mjs ../tools/rules-reference/rules.test.mjs` (164 tests). `test/v4.test.mjs` includes a line-for-line port of Zaphod's VS2 reader to show the new parser reads the same values, and runs the bundled standalone core.
- The standalone build names modules after their files and stops if two files share a name or an import would resolve to the wrong file (that once left the standalone without the necropsy rules).
- The IHC catalog is `../src/SeedData/ihc-assays.json`, made from the department's export by `node ../tools/ihc-import/convert_ihc_catalog.mjs "MHL IHC database.csv"`. The converter also rewrites `../docs/ihc-catalog-review.md`.
- Rebuild the standalone file after any change: `node build-standalone.mjs`.
- **The C# code is checked against this pilot.** After changing a rule in `core/ihc.mjs`, `pathology.mjs` or `necrules.mjs`, run `node ../tools/rules-reference/make_golden.mjs` to re-record the cases the C# tests replay, and `node ../tools/seed-sql/generate_seed_sql.mjs` if a dictionary or the assay catalog changed.
- Environment variables: `PORT` (default 3080) and `MHL_PILOT_DATA` (data folder).

## Troubleshooting

- **"Port 3080 is already in use"**: the pilot is probably already running in another window. Close it, or start with another port: `set PORT=3090` then `node server.mjs --open`.
- **"Node.js was not found"**: install Node.js LTS from nodejs.org (or ask IT), or use the standalone file in `dist/`.
- **The page looks out of date after an update**: refresh the browser (Ctrl+F5).
