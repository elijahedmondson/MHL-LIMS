# MHL LIMS — starter code (v0.2)

This is the first slice of the in-house LIMS described in the MHL LIMS roadmap (kept outside this repository): the database schema, the solution structure, the price list and charge rules with tests, and a working pilot. Version 0.2 moves the pilot's IHC and pathology rules and tables into the C# code and the SQL schema (roadmap Section 7.3).

> **Want to try it?** The working pilot is in `pilot/`. Double-click `pilot/Start MHL LIMS pilot.cmd` (needs Node.js 18+), or open `pilot/dist/MHL-LIMS-pilot-standalone.html` in Edge or Chrome. See `pilot/README.md` for a 30-minute walkthrough.

> **Read this first: the C# has not been compiled yet.** It was written in an environment without the .NET SDK. Expect a handful of small compile fixes on the first build. The business rules were checked another way. The price list and charge rules are also implemented in JavaScript (`tools/rules-reference/rules.mjs`), and 12 Node.js tests covering the same cases as the xUnit tests pass. The IHC and pathology rules were ported from the pilot, and `tools/rules-reference/make_golden.mjs` recorded the pilot's answers for about 1,500 cases in `tools/rules-reference/golden/ihc-pathology-golden.json`; the xUnit tests in `tests/MhlLims.Domain.Tests/Golden` replay them against the C#. A review that simulated the C# logic against those cases found no differences, but only a real `dotnet test` proves it. The SQL scripts have not been run against SQL Server yet either.

## Getting started

Prerequisites: .NET 10 SDK, SQL Server 2019 or later (LocalDB is fine for development), and Visual Studio 2022 17.14+ / Visual Studio 2026 or VS Code with C# Dev Kit.

1. **Create a development database** and run the scripts in SQLCMD mode from the `db` folder:
   `sqlcmd -S "(localdb)\MSSQLLocalDB" -d MhlLims_Dev -E -I -f 65001 -i deploy_all.sql`
   (Create the empty database first. `-I` matters: filtered indexes need QUOTED_IDENTIFIER on. `-f 65001` reads the seed scripts as UTF-8, so names such as "β-gal" load correctly. In SSMS, turn on Query > SQLCMD Mode and set `DbPath` at the top of `deploy_all.sql` to the folder's full path.)
2. **Restore and build:** `dotnet build MhlLims.slnx`. If your Visual Studio cannot open `.slnx` files, create a classic solution with `dotnet new sln -n MhlLims` and `dotnet sln add` each project.
3. **Run the tests:** `dotnet test`.
4. **Run the web app:** set the connection string with user secrets (`dotnet user-secrets set ConnectionStrings:Lims "<connection string>" --project src/MhlLims.Web`), then `dotnet run --project src/MhlLims.Web`. The CY2027 price list loads as DRAFT, so approve it (see `docs/price-list-review-CY2027.md`) before charges can be priced.
5. **Check the JavaScript reference** at any time: `node --test tools/rules-reference/rules.test.mjs`.

## Working conventions

- **Business rules live in `MhlLims.Domain`** and nowhere else, with a unit test for every rule. When a rule changes, change it in C#, mirror it in `tools/rules-reference/rules.mjs`, and update both test files until the price list and charge logic are stable.
- **The schema is owned by the SQL scripts** (ADR 0002). A change is a new numbered script; EF Core only maps to the result.
- **The pilot is the living specification for the IHC and pathology rules** (ADR 0005) until the production screens replace it. When the lab settles a rule, change it in the pilot (`pilot/core/ihc.mjs`, `pathology.mjs`, `necrules.mjs`), run the pilot tests, re-record the cases with `node tools/rules-reference/make_golden.mjs`, then change the C# until `dotnet test` passes. If dictionaries or the assay catalog change, regenerate the seeds with `node tools/seed-sql/generate_seed_sql.mjs`.
- **Price lists come from the billing worksheet** through `tools/price-list-import/convert_price_list.py`, which also writes the review of anything that looks wrong.
- **Record decisions** as short ADRs in `docs/adr/`.

## Suggested next steps (Phase 1)

1. First build: fix compile errors, run the tests, run `deploy_all.sql` on a dev server, and commit everything to the institutional Git repository.
2. Switch Blazor pages to `IDbContextFactory<LimsDbContext>` (one short-lived context per operation; the current scoped context lives as long as a circuit).
3. Map AD groups to the roles in `sec.Role` and add authorization policies per page.
4. Build the nightly legacy replica (PHL tables in FASDATA, the archive database, Zaphod) into staging, with `legacy.IdCrosswalk`, so the lookup shows real history.
5. Build the NAS sync (read `nas_information` into `lims.NasRequest`) and the request intake service behind the pilot's intake flow.
6. Add a CI pipeline that builds, runs the C#, reference and pilot test suites, and rebuilds the standalone pilot.
7. Put the pilot in front of necropsy, pathology, IHC and billing staff. Record what they change in `docs/open-questions.md` before building the Blazor versions of those screens.
8. Find who hosts phlrequest.ncifcrf.gov and get its schema and a full export, so IHC request history can be loaded into `ihc.IhcRequest` (keyed by `LegacyWebId`) and the catalog reloaded from the database rather than a CSV.

Open questions that block design choices are in `docs/open-questions.md`.
